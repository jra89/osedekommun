# Web IT-security training application

A website that looks like a Swedish municipality website called "Osede Kommun" that is supposed to have 1-3 instances of all vulnerabilities from OWASP Top 10 (and others).

Take website inspiration from sites like https://www.svedala.se https://www.skurup.se https://www.staffanstorp.se and so on (these are all real municipality websites).

# Requirements

* Divide all the tasks for this project into task files in a "tasks" folder. Each done task should be moved to "done" subfolder and each task should have a number after priority. This is so that we dont run out of context and can pick up single tasks to do individually at different times.
* Build the website in PHP with a MySQL database and with an Nginx web server or which ever is best as standalone
* There needs to be a control application written in Rust that can start and stop the website, database, etc.
 ** PHP, webserver, database server, etc should not require any installation and should preferably be all included and stand alone so one can just "run" it. When doing "./osede run" it will start everything that is needed, import SQL files etc if they are not already setup in the local folders for the application. "osede reset" will clear databases etc and reset everything to default. "./osede stop" simply stops the processes. Basically I want to be able to move the entire project folder to another Linux machine and just start it there.
* The website needs to be in swedish but have a little flag up in one corner where one can switch to english, but default swedish
* The web application / site needs to work without a domain to better function during education / course work for students.
* Document each of the vulnerabilities, where they are, how to use them, PoC if possible, what code is affected. Each one in its own file, numbers, and in a folder called "vulnerabilities". This folder should be outside of the web app web root so that it can be easily separated from the running application if needed so that students cannot find it using a vulnerability and cheat. But all built in vulnerabilities need to be well documented for easy checking when the student is done. Have a "Overview.md" with a checklist where the teacher (me) can go through what the student has found and check each one and perhaps discuss what was missed etc.
* The section "Idea for some of the vulnerabilities" must all be included but please fill in more and the ones I have missed or not yet mentioned (for now we are focusing on web applications and their vulnerabilities so OWASP Top 10 is a good one to go after).
* Do not comment the source code (basically its pretty common for sloppy applications to not be commented, so we want to mimic that)

# Ideas for some of the vulnerabilities

* A "login for municipality workers" where there's a user account called "ulla" with the password "Sommar2026" (passwords should be hashed in the database with md5).
* The front page should have some "news" where one can see "author" of said news, and all should be written by "ulla" (so student can figure out username that way).
* One of the news listed on the front should be written by "admin", but admin password should be "Aragorn2025!" and thus harder to guess (reachable via SQL injection that student can find by clicking on a specific news item to go to the page for that news item to read the entire post, which should have "id=x" in the URL with a blind SQLi). The SQL injection in question should only give access to a low privileged MySQL database account that only has access to the news and users tables.
* There should be a lot of humour on the website in the text, like one of the news posts written by "ulla" saying something like "Title: Bevattningsförbud! Body: Vi vill härmed påminna att det är strikt förbjudet att vattna trädgård, tvätta kläder, och annat, och helst faktiskt inte ens dricka från kranen. Det är inte särskilt mycket brist på vatten men kommundirektör Snåhl Djåp ska ha poolparty till helgen och behöver hinna fylla alla poolerna tills dess. Vi är tacksamma för att ni visar hänsyn till detta".
* One vulnerability, a file upload vulnerability, should be reachable by logging in with the administrator account, where the admin account can upload files that are legitimate images (so the student can upload a backdoor by uploading a filename.php that is an image, but has some php in the metadata headers of the image file, so the rest of the image file should be validated. Files should be uploaded to an upload folder of the website). The regular user "ulla" can see the upload functionality but will only see the message "You do not have authorization to upload files". The file upload is a "dangerous feature" and will require the administrator to enter their password before uploading (to prevent student from using the XSS to get to that point).
* The regular user "ulla" can write news posts and there should be an XSS vulnerability in the news rendering on the front page. The auth cookie should be missing important flags and can thus be stolen this way. The "osede" Rust binary should have an argument called "--adminvisit" which toggles a feature where it simulates the administrator visiting the website once a minute with a headless chrome or similar, so that if the student does an XSS attack to steal the admin cookie they will be able to do so. On the "user logged in" page where ulla can write news posts theres hould also be a menu alternative for "logs" that shows each visit to the front page, which then shows "user admin visited /pageX at xx:xx:xx" and "user ulla visited..." etc. The logs should be rotated every hour (or when they reach 1MB in size) to make sure they do not get too big.
* If the student steals the admin cookie and login then they cannot upload a file since they wont know the password yet, but there should be a notes function in the admin page (in the same menu as news, logs, etc) where the admin and ulla can create "personal notes" that they can save there. And the admin should have a note that says "Password reminder: you know what it is Elessar, Elfstone, Strider, heir of Isildur, ancient king of Arnor and Gondor". To give the student a hint to the password so they can try to crack the hash using hashcat or similar (which they will have to setup by their own).
* There should be a "private message" function with an inbox and the ability to write message to other users so admin and ulla can communicate. It should be possible to write messages to yourself (so student can test the function), and also delete messages in your own inbox of course. This feature should have an SSRF so the student can, if they choose, use this feature together with the XSS in the news posts to send the administrators cookie as a private message to ulla using javascript.
* An XSS with a javascript sink should be included somewhere. Make it so that it can be triggered with the inbox somehow (you decide how that works but it needs to be medium difficulty so not too hard to discover it) and that the "--adminvisit" also visits the admin inbox and reads all messages, so that the student can send a payload via message that triggers a sink in the inbox, as an alternative way to steal the admin auth cookie.
* Include a IDOR with missing authorization when fetching notes, so each note is an incremental ID number and if the student tries different IDs (even when logged out) it will simply return the note content. Start with fairly high numbers like "140" and then have a few numbers in between each so they have to actually iterate them a bit, so the "password hint" for admin could be "159". So when the student discovers the notes as ulla they can try doing that either by being logged in or not (but discovering it will of course usually require being logged in, but if they manage to guess the endpoint and parameters then all glory to them).
* Include some other features that have UNION based SQL injection and ERROR based SQL injection, so we cover those PLUS "detailed error messages / misconfigured web server" by having the ERROR based one. The vulnerable features could be the "password reset function" (dont actually send an email but create a password reset code in the database that is valid for 15 minutes and has 5 digits. The admin account cannot be reset this way, and if the student tries then they should get an error saying so. The request to send a password code by email should have the UNION sqli in the email parameter, and the request to enter the code to reset the password should have the error based one)).
* The request to enter the password reset code can also be brute forced so the code can be guessed and upon a correct guess the user can access a page where they can set the password for that account (in this case ulla). The "send password request" will say "enter email OR username to send a password reset code to". The code is not removed by simply guessing it right, but only after the password is actually reset OR when the timer runs out (actually timer running out does not remove it, but simply wont allow the user to continue even if the code is correct. So they would have to "send" a new code at that point).
* The MySQL database server should be of an old version where we can do the old "write module and include it to execute commands via the database server"-vulnerability. Be sure to include a PoC for this too that can be easily run and tested.
* Include an arbitrary file read vulnerability with a path traversal in the function that handles displaying images on the website. Basically "/image?file=images/theimage.png" which can then be used to read any file by traversing the system.
* Include a remote command execution vulnerability where the admin page (logged in as admin) has a menu item called "upload list" which lists all uploaded files in the upload folder, and when the user goes to that menu item / page it will do a POST request to an endpoint "/api/v1/uplist/" with the POST parameter "path=xxxx" where the xxxx is a ROT13 encoded/encrypted string which translates to "uploads/" which is decrypted on the server side and used in the function call "system('ls' + $_POST['path']);" which if the user realizes it is ROT13 they can then encrypt their own payload and execute commands that way. This API endpoint requires the user to be logged in as admin though but will not require the cookie. It will instead use a JSON token that the website fetches when logging in as admin, and is then sent with that API request in the Authorization header.
* Include a badly implemented JSON token Authoriation for the API endpoint where the JSON token does not correctly verify the signature (the token is not encrypted, only signed with a very long and secure key), so the student can try this and simply sign their own token, and since the application does not actually verify the signature it will work. Ulla will also get a token but with a value in the token "admin=0", so when ulla goes to the upload list page she gets an unauth error. This way the student can get a clue about what to try.
* Include an LFI vuln where the site has a "contact form" that the visitor can reach from the site top menu, that does some "include contactform.php" or similar. The log page on the logged in panel should be a txt log under "logs/" that should also log failed login attempts to the panel, which can then be used to poision the log file with PHP code, and when then used together with the LFI would execute the PHP code inside the log file.
* Open redirect (maybe in the login, like "redirectUrl=/dashboard", which then allows redirect to other domains)
